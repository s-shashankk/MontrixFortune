# MontrixFortune - Developer Guide ("understand this first")

An online furniture store. Customers browse products, fill a cart, check out with Cash on Delivery or
Razorpay (UPI / card / netbanking). Admins manage products, orders, payments, users and homepage banners.

Last reviewed: 2026-10-14. Where this file says "not verified", the statement comes from reading code only;
the app has not been compiled or run after the security hardening described in `DEPLOYMENT_READINESS.md`.

---------------------------------------------------------------------------------------------------

## 1. The big picture

```
 Browser (React SPA, Vite)                       Razorpay
 http://localhost:5173                           (payment gateway)
        |  JSON over HTTP, header                    ^   ^
        |  Authorization: Bearer <JWT>               |   | webhook (server -> server)
        v                                            |   |
 Spring Boot API (port 8080)  -----------------------+   |
   filters: RateLimit -> JWT -> Spring Security           |
   controllers -> services -> repositories (JPA/Hibernate)
        |
        v
   MySQL 8  (database "montrix_furniture", port 3306)
```

- Two programs: a **frontend** (static files in the browser) and a **backend** (a Java server). They only talk through the REST API.
- Both live in the same folder `MontrixFortune/`: frontend in `src/*.jsx`, backend in `src/main/java/...`.
- The backend holds no session. Every request carries a JWT; the server re-checks it each time (stateless).

| Layer | Technology | Version (from `package.json` / `pom.xml`) |
|---|---|---|
| Frontend | React, React Router, Axios, Tailwind CSS, Vite | React 19, Router 7, Vite 8, Tailwind 4 |
| Backend | Spring Boot (Web, Security, Data JPA, Validation), Lombok | Spring Boot 3.5.11, Java 21 |
| Auth | JWT with jjwt, BCrypt passwords | jjwt 0.11.5 |
| Database | MySQL (driver `mysql-connector-j`), Hibernate as JPA provider | MySQL 8 |
| Payments | Razorpay Java SDK + Razorpay Checkout JS | razorpay-java 1.4.4 |
| Tests | JUnit via Spring Boot test, H2 in-memory DB (tests only) | |

## 2. Running it locally

Needs: Java 21, Node.js, MySQL running on port 3306.

1. Create database `montrix_furniture` (tables are created automatically by Hibernate on first start).
2. Fill in `.env` (copy `.env.example`). Required keys:
   `DB_PASSWORD`, `JWT_SECRET`, `JWT_REFRESH_SECRET` (each 32+ chars), `RAZORPAY_KEY`, `RAZORPAY_SECRET`,
   `RAZORPAY_WEBHOOK_SECRET`, frontend `VITE_RAZORPAY_KEY_ID`. Optional: `DB_URL`, `DB_USERNAME`, `APP_CORS_ORIGINS`.
   The backend refuses to start if the JWT / Razorpay values are missing.
3. Backend (terminal 1): `.\mvnw.cmd spring-boot:run`  -> http://localhost:8080
4. Frontend (terminal 2): `npm install` then `npm run dev`  -> http://localhost:5173
5. First start seeds demo data (see section 8): categories, 150 dummy products, 3 hero slides, and demo accounts.

Frontend API address: `VITE_API_URL` (defaults to `http://localhost:8080`). It is baked in at build time (`npm run build`).

## 4. Database - what, how connected, how much

### Which database
**MySQL 8**, database name `montrix_furniture`. Nothing else. (H2 is used only by automated tests, in memory, and vanishes after each run.)

### How the app connects
- `application.properties` reads `DB_URL`, `DB_USERNAME`, `DB_PASSWORD` (defaults: `jdbc:mysql://localhost:3306/montrix_furniture`, user `root`).
- Spring Boot creates a **HikariCP connection pool**. Settings are not overridden, so the default applies: **max 10 connections**.
  Each request borrows a connection only while it runs a query. 10 connections comfortably serve a small shop.
- **Hibernate** (JPA) turns Java entities into SQL. `spring.jpa.hibernate.ddl-auto=update` (default, change with `DDL_AUTO`) creates and alters tables
  automatically at startup. That is convenient locally and **risky in production** (it never drops or renames; it can silently drift). Plan: Flyway migrations (checklist item 23).
- `OrderStatusEnumMigration` runs a raw `ALTER TABLE orders MODIFY order_status ENUM(...)` at every startup because `update` cannot change MySQL enum columns.

### Tables (10)
```
users ───< addresses
  │  └──── carts (1:1 per user) ───< cart_items >─── products >─── categories
  │
  ├───< orders >─── addresses (shipping address)
  │       ├───< order_items >─── products
  │       └──── payments (1:1 per order)
  └───< payments
hero_slides (homepage banners, independent)
```
| Table | Key columns / notes |
|---|---|
| users | email (unique), password (BCrypt hash), phone, role USER/ADMIN, is_active |
| addresses | belongs to a user; name, street, city, state, postal code, country, phone |
| categories | name (unique), description |
| products | name, description, price DECIMAL(10,2), stock_quantity, **image_url LONGTEXT**, category_id |
| carts / cart_items | one cart per user; item has quantity and a price snapshot |
| orders | order_date, total_amount, order_status, payment_method (COD/RAZORPAY), payment_collection_status (COD/PAID), shipping_address_id, user_id |
| order_items | price per unit **at time of purchase**, quantity, product_id |
| payments | razorpay_order_id, razorpay_payment_id (unique), signature, amount, payment_status, failure_reason, order_id, user_id |
| hero_slides | label, title, subtitle, image_url LONGTEXT, text position, display order, active |

Every table also has `created_at`, `updated_at`, `deleted_at` (from `BaseEntity`). `deleted_at` is not used anywhere yet (no soft delete is implemented).
Money is `BigDecimal` / `DECIMAL(10,2)` everywhere (max 99,999,999.99).

### How much can it store?
MySQL itself has no practical row limit (InnoDB tables go to tens of TB). The real limits are **disk space, RAM and query speed**.
Rough sizes (estimates, not measured):

| Data | Approx. size per row | 100,000 rows | 1,000,000 rows |
|---|---|---|---|
| User | ~0.5 KB | ~50 MB | ~0.5 GB |
| Order + ~3 items + payment | ~2 KB | ~200 MB | ~2 GB |
| Product (image as a URL) | ~1.5 KB | ~150 MB | ~1.5 GB |
| Product (image stored **inside** the DB as base64) | 100 KB - 5 MB | 10 - 500 GB | too big |

So: a normal furniture shop (thousands of products, hundreds of thousands of orders) fits in a few GB.
**Images are the one thing that can blow this up.** The admin product form uploads an image file and stores it as base64 text inside the row (`LONGTEXT`).
Fix: store images as files / object storage and keep only the URL (checklist item 25).
MySQL also has a limit on a single packet (`max_allowed_packet`, 64 MB by default on MySQL 8) which caps the size of one image upload.

### Why your normal (local) database cannot be used when deployed
`localhost:3306` means "MySQL on the same machine as the Java program". On a hosting service the program runs on a *different* machine, so there is no
MySQL at that address, and your PC is not reachable from the internet. You must give the deployed app a database that is reachable from the server:

| Option | Notes |
|---|---|
| MySQL container on the same VPS (docker-compose + a volume) | cheapest, you manage backups yourself |
| Managed MySQL (AWS RDS, DigitalOcean, Aiven, Railway, TiDB Cloud ...) | automatic backups, small monthly cost; free tiers change often - check current pricing |
| Keep your PC DB and expose it | **do not do this** (security, uptime) |

Moving your existing data: `mysqldump -u root -p montrix_furniture > backup.sql` on your PC, then import it into the new server with `mysql ... < backup.sql`.
Then set `DB_URL`, `DB_USERNAME`, `DB_PASSWORD` in the server's environment. Create a dedicated user (not `root`) with rights only on this database,
and allow connections only from the app server.
Do not copy the demo accounts/dummy products from section 8 into production.

## 5. How it works internally (flows)

### 5.1 Register / login / tokens
1. `POST /api/auth/register` -> email lower-cased, password BCrypt-hashed, role USER. Password rule: 8-72 chars, a letter and a digit.
2. `POST /api/auth/login` -> checks BCrypt hash and `is_active`; returns an **access token** (JWT, 1 hour) and a **refresh token** (JWT, 7 days). The JWT contains only the email.
3. The React `AuthContext` keeps `{token, refreshToken, user}` in `localStorage` (keys `montrix-auth`, `montrixToken`).
4. `api/axios.js` adds `Authorization: Bearer <token>` to every call. On a 401 it calls `POST /api/auth/refresh` once with the refresh token and replays the request. If that fails it clears the login.
5. On the server, `JwtFilter` validates the token, loads the user **from the database on every request**, and sets the role (`ROLE_USER` / `ROLE_ADMIN`). So blocking/deleting a user takes effect immediately.
6. Admin protection is in three places: `SecurityConfig` (`/api/admin/**` needs ADMIN), `@PreAuthorize` on admin controllers, and `ProtectedRoute adminOnly` in the React router (UI only; never trusted).
7. `RateLimitFilter`: max 10 login/register/refresh requests per minute per IP (in memory, so per server instance).

### 5.2 Browsing
- Home: `GET /api/products?page=&size=30` (paged), `GET /api/categories`, `GET /api/hero-slides`. All public.
- Product page: `GET /api/products/{id}`. Search: `GET /api/products/search?keyword=`. Category: `GET /api/products/category/{name}`.
- Prices come from the database; the browser's numbers are never trusted by the server.

### 5.3 Cart (`/api/cart`, login required)
- One `carts` row per user (created lazily). `POST /add`, `GET`, `PUT /update/{itemId}?quantity=`, `DELETE /remove/{itemId}`, `DELETE /clear`.
- Adding checks stock. Reading the cart refreshes each item's price to the current product price.
- `CartContext` only stores the item count for the navbar badge.

### 5.4 Checkout and orders (`/api/orders`)
`POST /api/orders {addressId, paymentMethod}` runs in one database transaction:
1. Load the user's cart; fail if empty. Verify the address belongs to the user.
2. For each cart item (sorted by product id) **lock the product row** (`SELECT ... FOR UPDATE`), check stock, subtract the quantity.
3. Create `orders` + `order_items` using the *current* product price; total = sum.
4. **COD**: status `CONFIRMED`, cart emptied. **Razorpay**: status `PENDING`, stock is held, cart kept until payment succeeds.
5. Anything that throws rolls everything back, so stock and orders never end up half-written.

Order statuses: `PENDING -> CONFIRMED -> PACKING -> OUT_FOR_SHIPMENT -> SHIPPED -> DELIVERED`, plus `CANCELLED` and `ORDER_FAILED`
(payment failed or expired). Admins can only move forward or cancel; DELIVERED / CANCELLED are final; ORDER_FAILED is set only by the payment system.

### 5.5 Online payment (Razorpay)
```
React Payment.jsx                 Spring Boot                          Razorpay
 1. POST /api/payments/create-order {orderId} ->  checks order is yours, unpaid
                                                  creates Razorpay order (amount from DB, in paise) ---------> 
                                                  saves payments row = PENDING
 2. <- Razorpay order id
 3. opens Razorpay popup (checkout.js) with VITE_RAZORPAY_KEY_ID  -------------------------------> customer pays
 4. <- payment id + signature (popup callback)
 5. POST /api/payments/verify -> recompute HMAC-SHA256(orderId|paymentId, RAZORPAY_SECRET)
                                  compare to signature -> payment SUCCESS -> order CONFIRMED, cart item removed
 6. (backup path) Razorpay -> POST /api/payments/webhook (signed with webhook secret)
                                  payment.captured -> same as step 5; payment.failed -> order ORDER_FAILED, stock restored
```
- Step 6 matters: if the customer closes the browser after paying, only the webhook can confirm the order.
- On failure (`/api/payments/fail` or webhook) stock is returned. `OrderExpiryJob` (every 5 min) does the same for `PENDING` Razorpay orders older than 30 minutes.
- If a payment is captured *after* expiry and stock is gone, the customer has paid without an order -> refund manually in the Razorpay dashboard.
- Secret key `RAZORPAY_SECRET` never leaves the server. Only the public key id is in the frontend.

### 5.6 Admin (`/api/admin/**`)
Dashboard counts (users, orders, products, payments) | users list (paged) | orders list + detail + change status + mark COD as paid |
products CRUD | categories list + create | payments list | hero slides CRUD + reorder.
Not available yet: block/unblock user (service method `updateUserStatus` exists but no endpoint calls it), edit/delete category, search/filter, export.

### 5.7 Scheduled work
`OrderExpiryJob` is the only one (needs `@EnableScheduling`, present on the main class). It uses the application server's local clock.

## 6. Security model (what protects what)

| Threat | Protection |
|---|---|
| Stolen passwords from DB | BCrypt hashes; hash is never serialised to JSON |
| Forged login tokens | JWT signed with `JWT_SECRET` (env var, 32+ chars) |
| Brute force | rate limit on auth endpoints |
| Seeing/changing other people's data | ownership checks in order / address / cart / payment services |
| Normal user calling admin APIs | role check at three levels (section 5.1) |
| Fake payment confirmation | HMAC signature check on verify + webhook |
| Wrong price / amount | price and total always computed on server |
| Overselling | row lock on product during order |
| Cross-site calls | CORS allows only `APP_CORS_ORIGINS`; CSRF disabled because auth is a header token, not a cookie |
| Info leaks | generic message for 500 errors, no stack traces, security headers |
Known weak spots: token in `localStorage` (readable by any XSS), no email verification, no password reset, in-memory rate limiter, no audit log.

## 7. Performance and optimisation - honest status

**Already reasonable**
- Stateless backend (can run several copies behind a load balancer; the rate limiter would then need Redis).
- Product list on the home page is paginated (30 per page); admin orders, users and payments lists are paginated.
- Money as `DECIMAL`, `LAZY` loading on most relations, admin order queries use `@EntityGraph` to avoid N+1 queries.
- Frontend is a Vite production build (minified, hashed file names): about 384 KB JavaScript + 54 KB CSS (uncompressed, in `dist/`).
- Stock handling is transactional and race-safe.

**Not optimised yet (in order of impact)**
1. **Images stored as base64 in `products.image_url` / `hero_slides.image_url`.** Each product list response can carry megabytes. Move images to files/CDN.
2. **Unpaginated endpoints**: `/api/products/search`, `/api/products/category/{name}`, `/api/admin/products`, `/api/payments/admin/all` load the whole table. The admin dashboard downloads *all* products just to show a count.
3. **No database indexes** beyond primary keys, unique constraints and foreign keys. `search` uses `LIKE '%word%'` which scans the table. Add indexes on `orders(user_id, order_date)`, `orders(order_status)`, `products(category_id)`; use full-text search for product search.
4. `Product.category` and `CartItem.product` are `EAGER`, `Cart.items` is `EAGER`: extra joins on every load.
5. **No caching** of rarely-changing data (categories, hero slides, product pages). A 60 s in-memory cache (Spring Cache + Caffeine) would remove most reads.
6. **No HTTP compression**: add `server.compression.enabled=true` (or let Nginx do gzip/brotli).
7. Entities are returned directly as JSON (no DTOs) in many endpoints, so extra fields travel and lazy-loading problems are hidden by `open-in-view` (kept on deliberately for now).
8. Frontend ships as one JS bundle; routes could be lazy-loaded (`React.lazy`) so shoppers do not download admin code.
9. Connection pool left at default 10; fine for a small shop, tune with `spring.datasource.hikari.maximum-pool-size` if needed.
10. Logging is minimal (4 log statements originally) - hard to debug in production.

**Realistic capacity** (rough estimate, not load-tested): one small VPS (2 vCPU / 2-4 GB RAM) should handle a small shop with tens of concurrent
shoppers. Load-test before a big sale (e.g. k6 or JMeter) rather than trusting this number.

## 9. Conventions and gotchas for new developers

- Backend layering: Controller (HTTP only) -> Service interface -> `serviceImpl` (logic, `@Transactional` where data changes) -> Repository.
- Responses are **not consistent**: many endpoints wrap in `ApiResponse {success, message, status, timestamp, data}`; some (products list, payments, addresses) return raw JSON.
  The frontend handles both with `response.data?.data || response.data`. Keep that in mind when adding endpoints.
- Two `ErrorResponse` classes exist (`dto/` and `exception/`) - only the `exception` one is used by the handler.
- Lombok (`@Data`, `@RequiredArgsConstructor`) generates getters/constructors; enable annotation processing in your IDE.
- To add a column: change the entity -> with `ddl-auto=update` Hibernate adds it locally. In production use a Flyway migration (once item 23 is done).
- Enums stored as strings; MySQL columns are real `ENUM`s, so adding an enum value needs an `ALTER TABLE` (that is why `OrderStatusEnumMigration` exists).
- Dates are `LocalDateTime` in the server's time zone (no zone stored). Set the server time zone deliberately (e.g. `TZ=Asia/Kolkata`).
- The frontend decides admin vs user from `auth.user.role`; this is only for showing/hiding pages. The server is the real gatekeeper.
- Do not put secrets in `VITE_*` variables: they are public in the browser. Only the Razorpay *key id* belongs there.
- Never commit `.env`. It holds database, JWT and Razorpay secrets.
- `src/test-apis.js` / `src/test-cart.js` are manual scripts, not part of a test suite.
- `target/`, `dist/`, `node_modules/`, `MontrixFortune.zip` (in the parent folder) are build output / archives; keep them out of git.

## 11. Deployment picture (target)

```
Internet --HTTPS--> Nginx (443)  --/        -> static React build (dist/)
                                 --/api/*   -> Spring Boot jar (port 8080, private)
                                                   |
                                                   v
                                      MySQL (managed or container, private network, backups on)
Razorpay --webhook--> https://yourdomain/api/payments/webhook
```
Steps: build frontend with `VITE_API_URL` set to the public API address -> `npm run build`; build backend `.\mvnw.cmd -DskipTests package` -> run the jar with
environment variables (DB, JWT, Razorpay, `APP_CORS_ORIGINS=https://yourdomain`) -> Nginx + Let's Encrypt -> add the webhook URL + secret in the Razorpay dashboard.
Use test keys until a full test purchase works, then switch to live keys.
